# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What is litek8s

A lightweight Kubernetes in one Rust binary, aimed at local development, home labs and cheap, heterogeneous edge hardware. `litek8s apiserver` serves the real Kubernetes API (`src/kube/`: object store, controllers, scheduler, DNS, service proxy and node agent in one process; kubectl, Helm and Argo CD work unchanged), measured by the compatibility corpus in `compat/` and the official conformance suite. Around it: local dev clusters (`litek8s dev`), a Docker Engine API, a terminal UI, built-in observability, an MCP server, and installing servers and nodes over SSH. (The original Docker-backed daemon with its own `litek8s.dev/v1alpha1` manifests and the distributed LLM experiment were removed in 0.2.0; CHANGELOG.md lists their replacements.)

## Build & Test Commands

```bash
cargo build                    # build
cargo test                     # unit + in-process API tests (no Docker needed)
cargo nextest run              # the same as CI runs them (.config/nextest.toml; CI also runs compat L0/L1 and examples/github-actions, docs/ci.md)
cargo run -- apiserver --kubeconfig /tmp/litek8s.kubeconfig   # API server + controllers + a local node
KUBECONFIG=/tmp/litek8s.kubeconfig kubectl create deployment web --image=nginx
```

Product vs development on one machine: the released litek8s (Homebrew) uses the default paths; `dev/lk <args>` runs this checkout's `target/release/litek8s` (rebuilt when stale) with `LITEK8S_HOME=~/.litek8s-dev` (own VM, clusters, sockets, kubeconfig, `lkdev-` contexts; `dev/lk build-vm` builds the VM guest from the checkout, `eval "$(dev/lk env)"` for DOCKER_HOST/KUBECONFIG). Never run a checkout build without LITEK8S_HOME against the user's own clusters. Non-release builds print `DEV <commit>` in `--version` and the UI header (build.rs; `LITEK8S_RELEASE=1` for releases).

Unit tests live next to the code (`#[cfg(test)]`). `tests/kube_apiserver.rs` exercises the API server over HTTP, `tests/ha.rs` a 3-server Raft control plane, `tests/obs_api.rs` the observability API, `tests/mcp.rs` drives `litek8s mcp` over stdio against an in-process API server; none needs Docker. Container execution on crun is only tested on Linux (bench/vm.sh); things that need a Docker API (the dev VM's guest build, bench/build-linux.sh, k3d baselines) can use litek8s's own (`eval "$(dev/lk env)"` or `eval "$(dev/stable.sh env)"`, see docs/develop-without-docker.md).

Kubernetes compatibility corpus (needs kubectl, perl, python3; L4 needs helm):
```bash
cargo run --release -- apiserver --kubeconfig /tmp/litek8s.kubeconfig &
KUBECONFIG=/tmp/litek8s.kubeconfig compat/run.sh --tiers L0,L1
compat/baseline-k3d.sh          # reference score on real k3s; every case must pass there
```

Official conformance suite (e2e.test v1.33, ~30 min; scores in `compat/CONFORMANCE.md`):
```bash
KUBECONFIG=/tmp/litek8s.kubeconfig compat/conformance.sh --target litek8s
```

To run a single test:
```bash
cargo test discovery_and_default_objects
```

## Architecture

**kubectl / Helm / litek8s CLI → Kubernetes API server (object store, WAL or Raft) → controllers + scheduler → node agents (crun or Docker) over one connection each**

- **CLI** (`cli.rs`) — clap commands grouped in the main help (the test `main_help_lists_every_command` keeps the list in sync). Most are clients of the Kubernetes API of the current kube context (`top`, `tree`, `logs`, `query`, `alerts`, via `ui::client::Endpoint`); `apiserver`, `agent`, `lb` run servers; `dev`, `install`, `cluster` manage clusters. `main.rs` dispatches the per-container shim, the dev sandbox/VM stages and `docker-fs` before the tokio runtime starts.
- **Kubernetes API server** (`kube/`) — `litek8s apiserver`. Generic JSON object store with an append-only WAL (`store.rs`), resource registry incl. CRDs (`registry.rs`), discovery incl. aggregated v2 (`discovery.rs`), OpenAPI v2 (JSON and the gnostic protobuf client-go's `OpenAPISchema()` decodes, which Argo CD's server-side diff needs) and per-group-version v3 with upstream's 1.33 built-in definitions (vendored `openapi/swagger.json`, embedded gzipped by `build.rs`, inflated per request) plus the CRDs' schemas (`openapi.rs`, `openapi_pb.rs`), merge/JSON/strategic patch and simplified server-side apply (`patch.rs`), selectors, server-side tables, watch with resourceVersion resume (`server.rs`), admission webhooks (`admission.rs`), API aggregation for APIServices (`aggregator.rs`), TLS on the same port for in-cluster clients (`tls.rs`). CRD schemas are checked like upstream (`crd_schema.rs`: CEL rules type-checked and cost-estimated at CRD create, pattern/format/value validation, ratcheting and CEL rules on objects; CEL itself in `cel/`), and every write records managedFields with server-side apply ownership, conflicts and pruning (`managed.rs`); see docs/crds.md. `protobuf.rs` decodes kubectl's protobuf request bodies using the vendored `proto/` schemas, compiled by `build.rs` with protox.
- **HA control plane** (`kube/ha/`) — `apiserver --cluster-init` / `--server URL --token T`: 3 or 5 servers share the object store through Raft (openraft 0.9). The log carries store `Mutation`s with their preconditions; each server's state machine applies them to its in-memory `Store` (`sm.rs`, snapshots in the WAL record format), so resourceVersions and watch history are identical everywhere. On-disk log in preallocated, CRC'd segments written by a flusher thread (`log.rs`; the Raft core never blocks on the disk); Raft runs on its own runtime and listener (API port + 1, `net.rs`). Client writes are forwarded to the leader whole, internal writes as deduplicated proposals; reads and write handlers pass a ReadIndex barrier (the leader's read index covers its whole log: a restarted leader resumes its term). Controllers and other singletons run only on the leader, fenced. `litek8s lb`, `server list|remove` in `lb.rs`; Jepsen-lite checker + workload in `lincheck.rs` (`tests/ha.rs`, `litek8s ha-check`). Docs: docs/ha.md; VM bench: bench/ha.sh, bench/HA.md.
- **Controllers** (`kube/controllers/`) — in-process, driven by the store's change feed: Deployment, ReplicaSet, StatefulSet, DaemonSet, Job, CronJob, ownerReference GC, the scheduler (binds pods to Nodes, spreads replicas of one owner, provisions local PVs), Service status/Endpoints, Event TTL, node lifecycle (`node_lifecycle.rs`: Lease expiry → Unknown, unreachable/not-ready taints, pods NotReady, eviction by tolerationSeconds, pod GC of deleted nodes). No-op writes are skipped so the loop settles; each work key has at most one pending timer.
- **Joining nodes** (`kube/join.rs`) — the server keeps a join secret and prints a k3s-style token `K10<sha256 of CA PEM>::<secret>`; `litek8s agent --join https://... --token ...` fetches `/cacerts`, pins it, `POST /apis/agent.litek8s.dev/v1/join` (node password check, pod CIDR allocation from `--cluster-cidr`), then opens the authenticated agent connection. Heartbeats on that connection renew Leases in kube-node-lease. Pod overlay: kernel WireGuard set up over generic netlink (`vpn/wireguard.rs`, peers changed in place so sessions and roamed endpoints survive), `kube/agent/overlay.rs`, peers pushed per node by the server from Node annotations. Across NAT (docs/networking.md): agents probe each directly routed peer every 10 s (a UDP datagram to its overlay address; WireGuard's passive keepalive answers, plain keepalives end up one-sided) and judge it (rx in 40 s + fresh handshake = direct; relayed: a handshake since the switch), reporting `OverlayStatus`; the server keeps it in `litek8s.dev/wireguard-peers` and computes routes in `kube/agent/relay.rs` (pure: a pair is relayed only if a side reports it unreachable, through a relay both reach — servers or `litek8s.dev/relay=true`, rendezvous-hashed, same from both sides), written to `litek8s.dev/wireguard-routes`; on each side the relay's peer gets the other's pod CIDR (kernel forwarding, `LITEK8S-OVERLAY` chain only on relays, pod CIDRs only), the direct entry stays without allowed IPs to keep probing; silent peers rotate through announced/observed endpoints (reaches port-forwarded or full-cone NATs; two Linux NATs cannot punch, they stay relayed). `--node-external-ip` for cloud VMs. Overlay metrics `litek8s_overlay_*`. E2E: `bench/nat-e2e.sh` (3 VMs, two homes in netns behind NAT), compat tier M2 (`compat/cases/M2-relay.sh`). Multi-node test bed: `bench/cluster.sh` (VMs on a LAN via `bench/lanhub.py`), cross-node cases in `compat/cases/M1-multinode.sh` (`--tiers M1`), soak in `bench/soak.sh` / `bench/SOAK.md`.
- **Server install** (`install.rs`) — `litek8s install server|agent [flags]` (root, systemd): fills in defaults (`--listen 0.0.0.0:6443`, `/var/lib/litek8s/{apiserver,node-agent}`, `--runtime crun`, detected `--node-ip`, `--kubeconfig /etc/litek8s/kubeconfig.yaml`), validates the flags with the real clap parser (`cli::parse_service_args`), checks prerequisites, copies the binary to /usr/local/bin, writes `litek8s-server|agent.service` (KillMode=process, Restart=always) with the token in `/etc/litek8s/<role>.env` (`LITEK8S_TOKEN`, read by both `apiserver` and `agent`), restarts it and waits for /readyz or the Node Ready. `litek8s uninstall [--purge]` kills pods via `/sys/fs/cgroup/litek8s/cgroup.kill` and removes bridge, WireGuard link, LITEK8S-* iptables chains and netns mounts. `install.sh server|agent ...` installs the binary (and crun/iptables) and runs it. E2E on two VMs: `bench/install-e2e.sh`.
- **Install over SSH and cluster files** (`remote.rs`, `cluster.rs`) — `litek8s install server|agent --ssh user@host` / `uninstall --ssh`: shells out to the user's `ssh` (their config, agent, known_hosts), one command per step: a probe (`uname`, sudo mode, installed version and sha256, tools), the binary (kept if identical; else `--binary` or a static Linux self, uploaded with `cat`; else the release of this version, fetched by the remote's curl and checked against SHA256SUMS; DEV builds need `--binary`), crun/iptables from the package manager, then `sudo litek8s install ...` with `LITEK8S_INSTALL_RESULT=1`: install.rs then skips the restart when binary, unit and env file are unchanged and ends with a `@@litek8s-install-result@@` JSON line (changed, node, join URL, token, CA). Token via a 0600 file; a sudo password is asked here and fed to `sudo -S`. A server's context goes into the local kubeconfig with the CA and `tls-server-name: kubernetes.default.svc`. `litek8s cluster apply|status|delete -f` (kind `Cluster`, `litek8s.dev/v1`): servers in order (the first `--cluster-init` when several), context `<name>`, agents in parallel, then labels/taints by merge patch; Nodes carry `cluster.litek8s.dev/{name,role,ssh,labels,taints}` annotations, so apply removes only what it set and finds agents that left the file (`--prune`: drain, uninstall, delete). E2E: bench/cluster-e2e.sh (3 VMs). Docs: docs/clusters.md.
- **Node agent** (`kube/agent/`) — runs the pods bound to its node. One persistent framed connection to the API server (`protocol.rs`; in-process pipe locally, HTTP upgrade for `litek8s node-agent --server ...`) carries pod events, status and multiplexed log/exec/port-forward streams (`hub.rs` is the server side). Pods run behind the `PodRuntime` trait (`runtime.rs`), picked with `--runtime auto|crun|docker` (auto = crun on a Linux host with crun installed, running as root, else Docker):
  - **crun** (`crun/`, Linux, no daemon): images pulled for the host platform into a content-addressed store, one unpacked dir per layer (`image.rs`), through the registry configuration (`src/registries.rs`: k3s's registries.yaml, mirrors tried before the registry, per-host CA/client cert/credentials; `--registry-config`, default /etc/litek8s/registries.yaml; `dev up` ships `Paths::dev_registries`, `install --registries`; docs/registries.md); overlayfs rootfs per container; OCI `config.json` with Docker-equivalent defaults (`spec.rs`); pod network/IPC namespaces kept as bind mounts in /run/netns (no pause container) on the `litek8s0` bridge with on-disk IPAM (`net.rs`); one `litek8s crun-shim` per container (same binary, dispatched in `main.rs` before tokio) that runs crun, writes CRI-format logs and the exit status, so containers survive agent restarts (`shim.rs`). Unit tests cover config.json, overlay args, IPAM, logs and unpacking; container execution is only tested on Linux (see bench/vm.sh).
  - **Docker** (macOS dev): a busybox sandbox owns the network namespace, containers join it.

  `kubelet.rs` serves `/metrics/resource` on :10250.
- **Local dev clusters** (`src/dev/`) — `litek8s dev up|down|status|delete|load|list --name <n> [--nodes N]`. One environment per machine (`env.rs`): a Virtualization.framework VM on macOS (`vm.rs` host side, `guest.rs` PID 1), a rootless sandbox on Linux (`supervisor.rs` host side, `sandbox.rs` stage 1 / PID 1), started with the first cluster and stopped with the last; the CLI talks to it over `<dev data>/env.sock`. Inside, `cells.rs` (`litek8s dev __cells`) runs every node of every cluster in a cell: the sandbox's namespaces again (net, mount, PID, cgroup `/cells/<cluster>/<node>`, UTS, IPC) on the `lkcells0` bridge (10.231.0.0/24). Linux hands each cluster's host sockets (API listener, docker.sock, broker, log) to its cell by SCM_RIGHTS; macOS relays over vsock (`tcp <port> <cell>` setns()es into the cell). Workers join with the real join flow and the WireGuard overlay. Paths and names per cluster: `cluster.rs` (default `dev` keeps the old ones). Docs: docs/dev.md. Startup race check: `bench/dev-multinode-loop.sh [runs]` (the multi-node example on one cluster stopped and started again; every pod must have the cluster DNS alone; CI job `multi-node loop`). Agents that connect while `apiserver` is still starting wait for `ApiState::agents_welcome` before their Welcome (cluster DNS, overlay endpoint).
- **Docker API** (`src/docker/`) — the Docker Engine API on the crun runtime's pieces, served by `litek8s dev` on `~/.litek8s/docker.sock` (or `apiserver --docker-socket`). Docker containers are runtime-level containers, not Pods (`engine.rs`: records in `<data>/docker/containers/<id>/container.json`, writable layer kept between runs, the crun shim with `--keep-rootfs` and an attach socket), networks are bridges with file IPAM and names answered by the cluster DNS server (`network.rs`), the image store is shared with pods (`images.rs`), `build/` is a classic-API builder (RUN in crun on an overlay whose upper dir becomes the layer; BuildKit Dockerfile syntax). `api.rs` routes and hijacks; `fs.rs` is `litek8s docker-fs` (archive in/out of a container's mount namespace). Corpus: `compat/docker/run.sh`; docs: docs/docker.md.
- **Observability** (`src/obs/`, docs/observability.md) — built-in metrics, log search and alerts instead of kube-prometheus-stack + Loki. `tsdb/`: embedded time-series store (Gorilla chunks, WAL, 2 h block files sealed and downsampled into 1 min / 10 min tiers, retention, series budget), data in `<data dir>/obs`. `node.rs`: what each node agent samples (cgroups, /proc, veths, PV use; cAdvisor/node-exporter names), sent as `Metrics` messages on the agent connection (`kube/agent/obs.rs`, gated by `Hello.features`/`Welcome.obs`). `kube_state.rs`: kube-state-metrics series from the store. `promql/`: PromQL subset; `api.rs`: Prometheus HTTP API under `/prometheus`, `/litek8s/v1/logs` (fan-out `LogQuery` streams to agents, which grep their CRI files and the archive of removed containers, `logs.rs`), `/litek8s/v1/alerts`. `alerts.rs`: built-in rules + `AlertRule`/`AlertReceiver`/`Silence` CRDs (group observability.litek8s.dev), webhook/ntfy/Telegram (`notify.rs`). `resource_metrics.rs`: `metrics.k8s.io/v1beta1` (NodeMetrics/PodMetrics, what metrics-server serves; `kubectl top`) from the store, a built-in group with no APIService object; an APIService `v1beta1.metrics.k8s.io` (metrics-server's) takes it over and deleting it gives it back (`kube/aggregator.rs`). CLI `litek8s logs|alerts|query|top` (`cli.rs`; `top` uses the legacy daemon only when its socket answers, else the kube context's metrics API). Tests: unit tests per module, `tests/obs_api.rs`; bench phases `obs-k3s`/`obs-litek8s` in bench/run.sh.
- **Agents** (`src/mcp/`, `skills/litek8s/`, docs/agents.md) — `litek8s mcp`: an MCP server on stdio (JSON-RPC lines, `mod.rs`) whose tools (`tools.rs`) answer in JSON: dev clusters (child `litek8s dev` processes: nothing but JSON-RPC may reach stdout), get/describe with events and owner chain, server-side apply, delete, pod logs, log search, PromQL, alerts, Docker API basics, and `diagnose_pod` (`diagnose.rs`: pure rules over pod, node and events). Guardrails in `guard.rs`: `/version` must say `+litek8s` (asked without credentials, so exec plugins never run for other servers), destructive tools need `confirm: true`, `--read-only`, results cut to `--max-output` with a hint. It reuses the UI's client and Kubernetes ops (`ui::kube_ops`, `ui::kube_resources`). The skill and docs/*.md are compiled in (`resources.rs`): MCP resources and `litek8s skill [--install DIR]`. `-o json` on `dev status|list`, `query`, `alerts`, `logs`.
- **Terminal UI** (`src/ui/`) — `litek8s ui` (ratatui + crossterm); `clusters.rs` samples the Clusters view (only while it is shown). `app.rs` is all state and key handling with no I/O (keys → `Effect`s, backends → `Msg`s; tested with TestBackend at 80x24 in `tests.rs`), `view.rs` draws with `theme.rs` (the btop-like look: palette by color depth and terminal background, asked once with OSC 11 before the input reader starts; meters, graphs, status glyphs, key chips; an ASCII pass over the frame; `theme`/`background`/`ascii` in ui.yaml), `docker.rs`/`kube.rs` talk only to the public APIs (Docker socket with `/events`-driven re-lists, Kubernetes list+watch, SPDY port-forward client in `kube/spdy.rs`), `home.rs` samples the dev supervisor's state, `ctx.rs` switches docker/kubectl contexts, `exec.rs` is an interactive exec with the UI suspended. The Kubernetes view (`kube/`, k9s-style: `state.rs` keys and views, `rt.rs` effects, `informer.rs` Table list+watch, `gitops.rs` Argo CD Applications through the Kubernetes API: status, resources tree, sync as an `operation`, refresh annotation, terminate; shared with the MCP tools `applications_list|application_status|application_sync|application_refresh`) changes only litek8s clusters: other contexts are read-only unless in `writableContexts` (`KubeUi::access`, every mutating `KEffect` goes through `guard`). Dev settings live in `~/.litek8s/config.yaml` (`dev/config.rs`, read by `dev up`). Docs: docs/ui.md.

## Key Conventions

- Rust edition 2024. Error handling uses `anyhow::Result` with `.context()` chains.
- All async code uses `tokio` with full features.
- Config paths use XDG directories via the `directories` crate (the data directory; `~/.litek8s` for sockets and settings).
- Every per-user path comes from `config::Paths` (`src/config.rs`): with `LITEK8S_HOME` all of them are under it (unit test `litek8s_home_holds_every_path`). Do not build paths from `$HOME`, `ProjectDirs` or `~/.litek8s` elsewhere, and take context names from `Cluster::context()` / `config::context_prefix()`, never a literal `litek8s-`.
